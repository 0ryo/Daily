# 今日の課題を作る（daily-task）

先生役として、今日の課題を1つ作る。**解答・解答につながるコード・実装手順は書かない。** 先生役のルールは CLAUDE.md の「先生役の仕組み」に従う。

## 1. 状況を集める
1. `python3 .claude/scripts/teacher_context.py` を実行し、今日の日付・計画上の週・基準の学習時間・HEAD・未コミットの変更・直近の課題とレビューを得る。
2. 次のファイルを読む。
   - 今週の短期目標 `plan/short-term/week-XX.md`（XX は 1 の出力の週）。ファイルがなければ、先に `week` スキルの「6. 来週の短期目標を作る」の手順で今週の分を作って保存してから続ける（学習者には伝えない）
   - `progress/log.md`、`progress/weakness.md`
   - 直近の `tasks/` を2件と `reviews/` を2件（なければ読まない）
   - 必要に応じて `plan/goals.md`（中期目標は今月の節だけ）、`plan/checkpoints.md`。`plan/archive/`（旧計画）は読まない

## 2. 未コミットの変更を確認する
- 「未コミットの変更（学習用コードの場所）」が1件以上あれば、課題を作る前にその一覧（多ければ件数と主なディレクトリ）を示し、**先にコミットするよう促して、ここで止まる**。
- 学習者が「このまま進めて」と答えた場合だけ続ける。その場合は**必ず**、課題ファイルの「基準コミット」の行の下に `- 作成時点の未コミットの変更: ` として、該当するディレクトリと件数（例：`1013/`〜`1016/` の44件）を記録する。daily-review はこの行を見て、今日の差分から除外する。課題の内容がその変更を扱うものでも省略しない。
- 記録・設定ファイル（tasks/ など）だけの未コミットは止めずに、課題を保存したあと先生役がコミットする（課題が終わったとき〔daily-review の記録のあと〕に claude/MMDD-records ブランチで push・PR・main へのマージまで行う）。

## 3. 今日の位置を判定する
1. 直近の課題ファイルの「状態」を確認する。
   - 「未着手」または「未完了」の課題があれば、新しい課題を出す前に、その課題名・日付・未達成の完了条件を伝え、**「続ける」か「次に進む」かを学習者に確認して止まる**。
   - 学習者が「続ける」を選んだら、新しい課題は作らず、「6. 表示する」の 2〜5 でその課題を課題ページに開く（状態は変えない）。
   - 「次に進む」を選んだら、未完了の課題の状態を「未完了（持ち越し）」に変え、未達成の条件を今日の課題の「引き継ぎ」に書く。
   - 状態が「完了（パート2を持ち越し）」の課題があれば、確認せずに今日の課題を作る。持ち越したパート2の内容を今日の課題の「前回からの持ち越し」に書き、今日の課題の量をその分（目安30分）減らす。
2. 今週の短期目標の「課題」表から、今日の曜日の行を今日の課題の元にする。前日までの課題が遅れている場合は、遅れた行から順に進める（予定を後ろにずらす。終わらなかった行は来週の短期目標に回す）。短期目標の内容、遅れ、明日以降の予定は、学習者にチャットで伝えない（2026-11-01 に学習者から指示）。
3. その日が AIなし課題（CP）の日なら、通常の課題は作らず、`/test-noai` を使うよう伝えて止まる。
4. 今日の課題がすでに `tasks/今日の日付.md` にあれば、新しく作らずに「6. 表示する」の 2〜5 で課題ページを開く。

## 4. 課題を作る
- 課題は、その週の短期目標の目標・課題表・完了条件に沿った**新しい独立した題材**にする。過去の課題の改修を新しい課題の代わりにしない（計画がコピーしての改修を指定している日を除く）。
- `progress/weakness.md` の弱点のうち、今日の範囲と組み合わせられるものを**1つ**選び、要件（「守ること」など）の1項目として入れる。弱点がまだなければ、過去の範囲から1つ選ぶ。どの弱点を選んだかは管理用の行にだけ書き、課題文には「弱点」と書かない（2026-10-28 に学習者から指示。できていないことを突かれているように感じるため）。
- 課題の仕様はパート1・パート2の節にだけ書き、型（構造体・プロトコル・画面・関数）ごとに見出しを立てる。`2-1-1` のような階層の番号は振らない。レビューや説明問題では、型名・関数名・操作で指す。同じ仕様を2か所に書かない。
- 構造体の名前、プロパティ、関数の名前・引数・戻り値は、先生役が決めて示す（2026-10-28 に学習者から指示。示してよい）。学習者が書くのは関数の中身である。
- 説明問題は「説明問題」の節に置き、「〇〇のとき、〇〇が〇〇になるのはなぜか？」の形で、検索キーワードを添える。
- 説明問題とテストは、要件と食い違わないようにする。要件で「エラーを投げない」と決めた場合を、エラーの種類を聞く問題にしない（2026-10-30 の説明問題1の誤り）。
- 短期目標の課題表の行が `【設計】` で始まる日は、下の「設計課題の書き方」で作る。

### 設計課題の書き方（2026-11-14 に学習者から指示）
通常の課題は型名とシグネチャを示すので、学習者は日本語の仕様を Swift に直す練習に偏る。設計課題では、何を作るかと使うトピックだけを示し、型の分け方・名前・データの流れを学習者が決める。
- 課題文に書くもの：タイトル（何を作るかの1文）、作業場所・想定時間、「守ること」、「## 作るもの」（アプリが何をするかを2〜4文で）、「## 使うトピック」（使う API・フレームワーク・ライブラリと、入れ方の指定。例：Swift Package Manager で入れる）、「## 条件」（外から確かめられる品質を箇条書きで。例：メインスレッドを止めずに表示する、クラッシュしない、画像の縦横比を保って全体を表示する）、「確かめること」、「参考」。
- 課題文に書かないもの：型名、プロパティ、関数の名前・引数・戻り値、番号付きの処理の手順、画面の部品の配置。上の「構造体の名前…は先生役が決めて示す」と「型ごとに見出しを立てる」は、設計課題には当てはめない。
- 同じ結果を複数のやり方（別の API やライブラリ）で作らせる形にしてよい。その場合は、やり方ごとに「## パート1：〇〇で作る」のように分け、各パートに使うトピックと条件を書く。プロジェクトを分けるか1つの画面で切り替えるかは、学習者に任せると明記する。
- 新しいトピックは1つまでにし、残りは学んだことのあるトピックにする。外部の API の URL や、使うライブラリの名前は、課題文で指定してよい。
- 「条件」と「確かめること」は、採点で達成・未達成を判定できる書き方にする。「きれいに設計する」のような判定できない条件は書かない。
- 説明問題は、平日の課題と同じく1問までにする。弱点の1項目は「守ること」に入れる。
- 管理用の行に `- 形式: 設計課題` を足す。

### 課題文の書き方（2026-10-28 に学習者から指示。2026-11-11 に短い形へ変更）
学習者は課題文を、課題ページ（カレンダー付きの HTML）で上から一度だけ読む。一目で何をするかが分かる短さにし、読みながら「これは何のことだろう」と解釈し直す場面を作らない。課題ページは、下の見出しと書き方を手がかりにカードやチェックリストに組み立てるので、形を崩さない。

**短く書くための形（2026-11-11 に学習者から「全体的に文章が長すぎて読みにくい」）**
- 長さの目安は、平日の課題で、管理用の行と「途中で〜」の記録を除いて3,500字まで。
- タイトルの直後の引用（`>`）に、その日に作るものを1文で書く。
- 型ごとに「### 種類 `型名`」の見出しを立てる。種類は「構造体」「プロトコル」「画面」「関数」「列挙型」「クラス」のどれかにする（課題ページがこの言葉で色分けする）。見出しの直後に、その型の役割を1文で書く。パート2で同じ型に足すときも、同じ見出しを立てる。
- プロパティが2つ以上ある構造体は、「プロパティ｜型｜意味」の表にする。1つだけなら「- プロパティ：」の1行にする。
- シグネチャを示す関数は、コードブロックでシグネチャを示し、その下に「目的」「引数」「戻り値」を1行ずつ書く。目的は、その関数が何のためにあるかを1文で書く（2026-10-30 に学習者から「何をする関数か伝わらない」と指摘があったため、目的は省かない）。引数も戻り値もないときは「引数・戻り値：なし」の1行にまとめる。似た関数があるときは「〇〇との違い」を1行足す。
- 処理は番号付きリスト（`1.`）にし、1項目を「**いつ・どの関数**：何をする」の1行にする。主語が見出しの型と同じなら、主語を書かない。別の型が主語のときだけ型名を書く。
- `nil` のときに何もしないことなど、Swift の書き方で自然に決まる細部は書かない。採点に関わる失敗時の扱いだけを書く。
- 「確かめること」はチェックリスト（`- [ ]`）にし、1項目を「操作 → 操作 → 期待する表示」の1行で書く。課題ページは、最後の「→」の後ろを「期待する表示」として見せる。上から順に試すか、それぞれ独立に試すかを、見出しの直後に1文で書く。
- 説明問題は「### 説明問題」の見出しの下に、問いを1段落で書き、次の段落に「検索キーワード：`...`」を書く。
- 「## 参考」には、「- [ページ名](URL)：何を調べるときに読むか（短い句）」の形で並べる。

**読み手が迷わないための決まり**
- 前置きなしに物を出さない。型は見出しの名前から書き始める。
- まだ出てきていないものを前提にしない。JSON、テスト番号、前のテストの結果などは、出てきた後でだけ触れる。説明問題では、テスト番号（「テスト5」）や要件の番号（「4-4-3」）で場面を指さない。「UISwitch をオンにして保存に失敗したとき」「起動したときに読み込めなかったとき」のように、操作と結果、型名・関数名で場面を書く（2026-11-07 に学習者から指示。番号だと課題文を読み返さないと何のことか分からないため）。「前の3件」のような遠回しの言い方もしない。
- 指示語（これ、それ、その、この、あの、そのほか）を使わない。毎回、型名・関数名など対象の名前を書く。
- 作業の形式（Playground、コマンドラインツール、UIKit アプリ、SwiftUI アプリ）に合う言葉だけを使う。コマンドラインツールと Playground の日に「画面」「アプリ」と書かない（2026-10-30 の誤り）。
- 先生役が作った呼び名（「保存担当」など）を使わない。Swift の用語（構造体、プロパティ、関数、エンコード、デコード、呼び出し元）と、示した型名・関数名で書く。
- ヒントを避けるために言葉をぼかさない。エンコード・デコードなど、普通の用語をそのまま使う。
- 不要なことは「〜は不要」とはっきり書く（例：「CodingKeys は不要」）。
- 出力（print）は、何をどこで出すかを1か所で1回だけ書く。「ここでは出さない」と「あちらで出す」を両方書かない。
- 公式ドキュメントは、リンクごとに「何を調べるときに読むか」を添える。リンクだけを並べない。
- 先生役の判断の材料（弱点、計画のどの行か、確かめた・動いたという報告）は課題文に書かない。
- 平日の課題は、パート1とパート2を合わせて、新しい構造体を2つまで、「確かめること」を6項目まで、説明問題を1問までにする（2026-11-07 に学習者から「単純に量が多くて時間がかかった」。11/5 の課題は構造体3つ・テスト9件・説明問題2問で、想定2時間に対して3日・8〜9時間かかった）。
- 想定時間は、基準の学習時間より30分短くする（平日2h、土日6h）。実際は想定より長くかかるため（2026-10-28 に学習者から指示）。
- 課題は「パート1」と「パート2」に分ける（2026-10-30 に学習者から指示。毎日、想定時間を超えているため）。パート1は、その日の中心になる要件と、そのテストにする（平日の目安は1.5時間）。パート2は、残りの要件・テスト・説明問題にする。学習者はパート1だけで提出してよい。各パートの中に、そのパートの型と「確かめること」を、作る順に上から並べる。パートの範囲を一覧で示さない。全体にかかる「守ること」は、パートより前に1回だけ書く（2026-10-31 に学習者から「区切りがキモい。構造体はまとめて、上から順に要件を書いてほしい」と指示）。
- 新しい概念を初めて扱う日は、要件の一部をパーソンズ問題（正しいコードの行を順不同で示し、並べ替えさせる）や穴埋めにしてよい。並べ替えに使うコードは、課題の他の要件の解答にならない範囲にする。2日目以降の同じ概念では使わない。
- 作業場所は学習用コードの場所の中にする（通常は `MMDD/`。計画が `apps/App1/` などを指定していればそこ）。先生役はその場所にファイルを作らない。
- 「公式ドキュメント」には、Apple Developer Documentation のページ名や The Swift Programming Language の章名などのトピック名と、**そのページの URL** と、何を調べるときに読むかを書く。URL は実在を確かめたものだけにする。関数の中身の解答になるコードと手順は書かない。

## 5-2. 送る前に、別の読み手に読ませる（2026-10-30 に学習者から指示）
保存した課題ファイルを、表示する前に `task-reader` サブエージェント（読み取り専用）に読ませる。task-reader は会話の履歴を見られないので、プロンプトに次を含める。
- 課題ファイルのパス、作業の形式（Playground／コマンドラインツール／UIKit／SwiftUI）
- このスキルの「課題文の書き方」の節を読むこと（`.claude/skills/daily-task/SKILL.md`）

task-reader の指摘は、課題の仕様と難しさを変えない範囲で、すべて課題ファイルに反映する。仕様の誤り（要件と説明問題・テストの食い違いなど）の指摘を直したときは、直した課題ファイルをもう一度 task-reader に読ませ、指摘が0件になってから表示する。指摘を反映しないと判断した項目は、その理由を管理用の行「読み手の確認」に1行で書く。

## 6. 表示する（2026-11-11 に学習者から指示。チャットに課題文を貼らない）
課題文はチャットに貼らず、課題ページ（カレンダー付きの HTML）で見せる。チャットに貼ると、返答チェックで書き直したときに古い版が会話に残り、学習者が遡ったときに古い要件を読んでしまうため。
1. 課題ファイルを保存・編集すると、PostToolUse フック（`answer_check.py --task-hook`）が課題ファイルの量と書き方を検査する。問題が返ってきたら課題ファイルを直し、通るまで次に進まない。
2. `python3 <記録の作業場所>/.claude/scripts/task_page.py` を実行し、記録の作業場所の `tasks/` から課題ページを作り直す。課題文はスクリプトがそのまま埋め込むので、先生役が書き直さない。
3. Bash の `run_in_background` で `python3 <記録の作業場所>/.claude/scripts/task_page.py --serve` を動かす（すでに動いていれば、そのまま終わる）。
4. ブラウザの表示欄（`mcp__Claude_Browser__navigate`）で `http://127.0.0.1:8765/tasks.html#YYYY-MM-DD` を開く。
5. チャットには、課題のタイトルと、課題ページを開いたことを短く書き、最後に1行で「終わったら『できました』と伝えてください」と添える。課題文・完了条件・テストはチャットに書かない。

課題ファイルは記録の作業場所でコミットする。課題ファイルを途中で直したとき（「途中で変えた条件」など）も、2〜4 で課題ページを作り直して開き直す。
