# 提出された課題をレビューする（daily-review）

先生役として採点し、記録する。**学習者のコードを書かない・直さない。修正案のコードや直し方の手順も出さない。** 先生役のルールは CLAUDE.md の「先生役の仕組み」に従う。

**課題は100点（全完了条件の達成）になるまで終わらない。** 70点以上の「合格」は目安であって、課題の終了ではない。100点未満なら、合格・不合格にかかわらず、結果の最後に「ここが残っています！直したら、もう一度『できました』と伝えてくださいね」のように、明るい言い方で明示する。「完了」「終わり」「ここまで」という言い方をしない。再提出は同じ reviews/ ファイルの末尾に追記し、100点になるまで繰り返す。

**採点と指摘は、その日の課題文の完了条件に書かれていることだけを対象にする。** 課題文にない要求（過去の課題の動作確認、PR の書き方の好み、課題が扱わない観点）を、再提出の条件に足さない。課題が扱わない観点は「適用外」とする。口調は CLAUDE.md の「口調と指摘の範囲」に従う（対等で丁寧、できた点を先に伝える、同じ指摘は1回）。

**途中で止まってよいのは次の3つだけ。** それ以外では、完了条件が未達成に見えても、必ず手順4（reviewer）と手順6（記録）まで進める。未達成は採点と記録で示す。
- 課題ファイルが1つもないとき（手順1）
- 差分から採点対象のファイルを特定できないとき（手順2-5）
- 学習時間と詰まった箇所の質問（手順6-3）

## 1. 対象の課題を決める
1. `python3 .claude/scripts/teacher_context.py` を実行する。
2. 対象の課題ファイルを決める。
   - 今日の日付の `tasks/YYYY-MM-DD-cpN.md`（AIなし課題）で状態が「実施中」のものがあれば、それを優先する。
   - なければ `tasks/今日の日付.md`。
   - それもなければ、状態が「未着手」「未完了」の最新の課題ファイル。どれを採点するかを1行で伝えてから進める。
   - 課題ファイルが1つもなければ、採点せずに「まず『今日の課題を作成してください』で課題を作ってください」と伝えて止まる。

## 2. 今日書いたコードを特定する
1. 課題ファイルの「基準コミット」を読む。
2. AIなし課題の場合は締め切り（開始時刻＋制限時間）を課題ファイルから読み、`git rev-list -1 --before="<締め切り>" HEAD` で締め切り前の最後のコミットを採点対象にする。締め切り後の変更は採点しない（未コミットの変更も採点しない）。経過時間を記録する。
3. 通常の課題の場合は、次の3つを合わせて「今日の差分」とする。
   - `git diff --stat <基準コミット> -- . ':!tasks' ':!reviews' ':!progress' ':!.claude' ':!plan' ':!CLAUDE.md' ':!README.md'` と、同じ範囲の `git diff`（作業ツリーと比べるため、コミット済みと未コミットの変更の両方を含む）
   - `git ls-files --others --exclude-standard`（未追跡のファイル）
   - 課題ファイルに「作成時点の未コミットの変更」が記録されていれば、それは除外する。
4. tasks/、reviews/、progress/、.claude/、plan/、CLAUDE.md、README.md の変更は採点対象から外す。
5. 差分から対象ファイルを特定できない場合（差分が空、または課題の作業場所と無関係な変更しかない場合）に**だけ**、どのファイルを採点するかを学習者に聞いて止まる。
6. 未追跡のファイルも、課題の作業場所の中にあれば必ず採点対象に含める。

## 3. ビルドと実行結果を集める
- 課題が Git の作法・PR・CI などコード以外を扱う場合は、証拠として `git log --oneline --graph -n 20 --all`、`git branch -a`、`gh pr list --state all --limit 10`、`gh pr view <番号>` の結果を集めて reviewer に渡す。
- Xcode プロジェクトなら、ビルド生成物をリポジトリの外に置いてビルドする：`xcodebuild -project <path> -scheme <scheme> -destination 'generic/platform=iOS Simulator' -derivedDataPath "${TMPDIR:-/tmp}/daily-review-dd" build -quiet`。テストターゲットがあれば `test` も実行する（destination は利用可能なシミュレータを `xcrun simctl list devices available` で選ぶ）。
- playground や Swift ファイル単体は、リポジトリの外にコピーしてから実行する。学習用コードの場所でファイルを作ったり変えたりしない。
- シミュレータで画面の表示（縦横、文字サイズ、制約衝突のログ）を確かめられる環境なら確かめる。できなければ「未確認」として reviewer に渡す。

## 4. reviewer に採点させる
Agent ツールで `reviewer` サブエージェントを呼ぶ。プロンプトには次をすべて含める（reviewer は会話の履歴を見られない）。
- 課題ファイルのパス（要件と完了条件はそこにある）
- `plan/rubric.md` を基準にすること、今週の計画ファイルのパス（テストの基準が第1〜5週と第6週以降で変わる）
- 採点対象のファイルの一覧と、`git diff` の結果
- ビルド・テスト・実行の結果（成功・失敗とエラー文、未確認の項目）
- 修正後のコードや直し方を書かないこと

## 5. 表示する
reviewer の結果を、次の順で表示する。reviewer の結果に直し方やコードが含まれていたら、その部分を削ってから表示する。
1. 完了条件の達成状況（条件ごとに達成・未達成）
2. ルーブリック5観点の採点と根拠（コードの該当箇所付き）
3. 良かった点（具体的に1〜2点）
4. 改善すべき点（どこが・なぜ問題か・どの観点か。直し方とコードは書かない）
5. 次に調べるべき公式ドキュメントのトピック名

## 6. 記録する
1. `reviews/YYYY-MM-DD.md`（AIなし課題は `reviews/YYYY-MM-DD-cpN.md`）に、冒頭へ「課題: tasks/…」「基準コミット」「採点対象のコミットまたは差分」「採点日時」を書き、続けて表示した内容をそのまま保存する。同じ日に再提出された場合は、ファイルの末尾に「## 再提出（HH:MM）」として追記し、前回の結果は消さない。
2. 課題ファイルの「状態」を更新する。
   - 完了条件がすべて達成、かつ合計が100点（5観点すべてがレベル4。適用外の観点を除く）→ 「完了」
   - それ以外（70点以上で合格の目安を満たしていても）→ 「未完了」とし、課題ファイルの末尾に「## 未達成の条件（YYYY-MM-DD のレビュー）」として未達成の条件を列挙する。翌日の daily-task がこれを引き継ぐ。
3. 学習者に、**1回だけ**まとめて次の2つを質問して止まる：「今日の学習時間（何時間）」と「詰まった箇所（なければ『なし』）」。
4. 回答を受け取ったら、`progress/log.md` の末尾に次の形式で追記する。

```
## YYYY-MM-DD（曜）第N週
- 課題: tasks/YYYY-MM-DD.md（区分: UIKit）
- 結果: 完了（100点）／未完了（再提出待ち）、合計 NN 点（動作 L/設計 L/可読性 L/テスト L/Swiftらしさ L）
- 学習時間: N.Nh
- 詰まった箇所: （学習者の回答をそのまま要約）
- 主な改善点: （観点：短く1〜3件）
```

5. 最後に、記録ファイル（tasks/、reviews/、progress/）を先生役がコミットする（main にいるときは先にブランチを切る。push と PR は学習者）。学習用コードのコミットは学習者に促す。
