# リーダブルコードの確認項目（レビューで毎回使う）

2026-11-20 に学習者から指示。学習者が参考にしている記事：[【リーダブルコード】リーダブルコードの要点 まとめ](https://zenn.dev/student_blog/articles/804a623a72742f)（書籍『リーダブルコード』の第1〜9章の要約）。

基準は「ほかの人（未来の自分を含む）が最短時間で理解できるか」。短いコードがよいとは限らない。読み手が頭の中で裏返したり、遡って確かめたりする手間が少ないほうを選ぶ。

## 指摘の扱い
- 毎回、今日の差分のすべてを下の項目で読む。当てはまる箇所がなければ「リーダブルコードの確認：気になる箇所なし」と書く。
- 指摘は**任意**として、優しく伝える。学習者のコードを使った書き換えの例と、読み手にとって何が楽になるかを1文で添える。
- 減点は、`plan/rubric.md` の「可読性」のレベル3以下に当たる場合だけにする（名前から役割が分からない、長い関数・重複が多いなど）。この一覧だけを理由に減点しない。
- 一度の指摘は最大3件にし、読みやすさへの効き目が大きい順に並べる。同じ種類は1件にまとめる。
- 「この段階でここまで作り込まなくてよい」も指摘の対象にする（下の「作り込みすぎ」）。逆に、その Phase で必要のない作り込みを求める指摘はしない。

## 確認項目

### 名前（第2・3章）
- 中身が分かる具体的な名前か。`data`・`tmp`・`result`・`flag` のような何にでも使える名前を、広い範囲で使っていないか。
- 動詞が処理に合っているか。ネットワークから取るなら `fetch`、ファイルから読むなら `load`、のように「どこから・どうやって」が伝わるか。
- 単位や中身の種類が名前から分かるか（`timeoutSeconds`、`photoFileName`）。
- 上限・下限は `max`・`min`、両端を含む範囲は `first`・`last` のように、境界を含むかが分かる名前か。
- Bool は `is`・`has`・`can`・`should` で始まる肯定の名前か（`isNotEmpty` や `disableX` のような否定の名前にしない）。

### 制御の流れ（第7章）
- 条件は肯定形を基本にしているか。`if !isValid { … } else { … }` のように、否定の条件を先に書いて else で本題を書く形になっていないか。否定の `!` が重なっていないか。
- 比較は、調べる値を左、比べる相手を右に書いているか（`count > maxCount`）。
- 失敗や対象外の場合を `guard` で先に返し、本題のネストを浅くしているか。
- 単純な場合・関心のある場合を先に書いているか。

### 大きな式（第8章）
- 長い条件や式を、意味の分かる名前の定数（説明変数・要約変数）に分けているか（例：`let isWornAfterWash = outfit.date > lastWashedAt`）。
- ド・モルガンの法則で、否定の組み合わせを読みやすい形に直せないか。

### 変数（第9章）
- 意味を足していない中間の変数がないか。
- 変数の範囲が必要以上に広くないか（関数の中で済むものをプロパティにしていない）。
- `var` で何度も書き換えていないか。`let` で一度だけ決められないか。

### コメント（第5・6章）
- コードを読めば分かることを、そのまま日本語にしたコメントがないか。
- 「なぜそうしたか」「あとで直すこと（`// TODO:`）」など、コードからは分からないことだけを書いているか。
- 分かりにくい名前をコメントで補っていないか（名前を直すほうが先）。

### 見た目のそろえ方（第4章）
- 同じことをする箇所は、同じ形・同じ順番で書いているか。
- 空行で処理の段落を分けているか。

### 作り込みすぎ（人間の都合で決める）
- その Phase で使わない protocol・汎用化・設定項目・エラーの種類を先に作っていないか（`plan/app-roadmap.md` の「実務の進め方」）。
- 1回しか使わない処理を、無理に共通の関数や拡張に切り出していないか。
- 短く書くために、三項演算子の入れ子や、読み手が展開しないと分からない書き方にしていないか。
