# コード評価ルーブリック

> この計画が想定する前提：毎日の課題・アプリ制作・AIなし課題のすべてを、このルーブリックで100点満点で採点する。以前の採点方式（仕様60・Swiftらしさ20・可読性20）は使わない。

## 点数の付け方
- 5つの観点（動作・設計・可読性・テスト・Swiftらしさ）を、それぞれレベル1〜4で判定する。
- 各観点の点数：**レベル4＝20点、レベル3＝15点、レベル2＝10点、レベル1＝5点**。ビルドできない、または提出がない観点は0点。
- 合計100点。採点では観点ごとのレベル・点数・根拠（ファイル名と行）を示す。
- 実行して確かめられなかった項目がある場合は、点数を「暫定」とし、何が未確認かを書く。
- 課題で扱っていない範囲（未習の技術、仕様にない機能）では減点しない。表示文言の細かな違いも減点しない。
- **課題文に書いていないことを、レベル4の条件にしない**（2026-10-30 に学習者と決定）。下の表のレベル4の条件のうち、その日の課題文が求めていないもの（自分で考えた確認ケースの列挙、`// MARK:`、protocol での差し替えなど）は、満たしていなくてもレベル4を付ける。課題文が求めたことをすべて満たし、表のレベル3以下に当たる問題がなければレベル4にする。
- 課題がパート1・パート2に分かれていて、パート1だけが提出されたときは、パート1の要件・テスト・説明問題だけで採点する。パート2の項目は「持ち越し」と書き、減点しない。

## 合否の目安
| 対象 | 合格の条件 |
|---|---|
| 毎日の課題 | 合計70点以上、かつ「動作」がレベル3以上 |
| AIなし課題（CP1〜CP5） | 合計70点以上、かつ「動作」がレベル3以上 |
| AIなし課題（CP6） | 合計75点以上、かつ「動作」と「設計」がレベル3以上 |
| 成果物アプリ（App1・App2） | 合計80点以上、かつ全観点がレベル3以上 |

合格しなかった場合は、最も低い観点について修正を求め、修正後の最新版をあらためて採点する。

## 観点別の判定基準

### 1. 動作
| レベル | 判定基準 |
|---|---|
| 4 | 課題のテストケースをすべて満たす。境界値・空データ・不正な入力・通信失敗でも期待どおりに動く。実機またはシミュレータで、縦向き・横向き・文字サイズ最大のときに表示が崩れず、**コンソールに Auto Layout の制約衝突（Unable to simultaneously satisfy constraints）が1件も出ない** |
| 3 | 正常系のテストケースをすべて満たす。異常系・境界値で1件だけ期待と異なるが、クラッシュはしない。制約衝突のログが出るが、表示は崩れていない |
| 2 | 正常系の一部が期待と異なる、または特定の操作でクラッシュする。もしくは制約衝突により表示が崩れる |
| 1 | 主要な機能が動かない |

### 2. 設計
| レベル | 判定基準 |
|---|---|
| 4 | 責務が分かれている：**ViewController（SwiftUI では View）は入力の受け渡しと表示だけを行い、検証・変換・保存・通信はモデル・ViewModel・Store などにある**。依存を protocol で差し替えられる。**循環参照がない**（デリゲートは `weak`、クロージャで `self` を保持するときは `[weak self]`、画面を閉じると `deinit` が呼ばれる）。SwiftUI では状態の所有者（Source of Truth）が1つに決まっている |
| 3 | 責務は概ね分かれているが、VC に整形や検証の処理が少し残っている（目安：1つの VC が200行を超え始めている）。循環参照はない |
| 2 | **VC が肥大化している**：検証・保存・通信のうち2つ以上を VC が直接持つ（目安：1つの VC が300行を超える、または `viewDidLoad` が50行を超える）。あるいは循環参照が1か所ある |
| 1 | 処理がほぼすべて1つの VC／View にある。または複数の循環参照があり、画面を閉じても VC が解放されない |

### 3. 可読性
| レベル | 判定基準 |
|---|---|
| 4 | 名前から役割がわかる（Swift API Design Guidelines に沿う）。1つの関数が1つの仕事をする（目安：30行以内）。`// MARK:` などで構成がわかる。マジックナンバーがなく、重複がない。コメントは「なぜそうしたか」だけを書いている |
| 3 | 名前と構成は概ねわかりやすい。長い関数や重複が1〜2か所ある |
| 2 | 名前から役割がわからない箇所が複数ある（`data`、`flag`、`tmp` など）。長い関数や重複が多い |
| 1 | 処理の流れを追うのに、実行して確かめる必要があるほど読みにくい |

### 4. テスト
自動テストを学ぶ前は「確認ケースの列挙と実行記録」で判定する。短期目標で自動テストを扱った週の次の週からは、自動テストで判定する（旧計画では第6週。2026-10-24 に週の固定をやめた）。

| レベル | 自動テストを学ぶ前の判定基準 | 自動テストを学んだ後の判定基準 |
|---|---|---|
| 4 | 正常系・異常系・境界値の確認ケースを自分で列挙し、全ケースの実行結果を PR に記録している | モデル・ViewModel のテストが正常系・異常系・境界値を含み、すべて通る。依存を差し替えて、ネットワークやファイルに触れずに動く。非同期処理のテストがある。CI で通る |
| 3 | 課題のテストケースを実行し、結果を記録している | 主要なロジックのテストがあり通るが、異常系か境界値が不足している |
| 2 | 一部のケースだけを確認している | テストはあるが、主要なロジックの一部しか確かめていない、または失敗したままのテストがある |
| 1 | 確認の記録がない | テストがない |

### 5. Swiftらしさ
| レベル | 判定基準 |
|---|---|
| 4 | 強制アンラップ（`!`）と `try!` がない（`@IBOutlet` を除く）。Optional を `guard let`・`if let`・`??` で扱う。値型（struct・enum）を基本にし、参照が必要なときだけ class を使う。`private`・`final` を適切に付ける。状態を enum で表す。Swift 6 言語モードで並行性の警告がなく、UI の更新を `@MainActor` で行う |
| 3 | 上の条件を概ね満たすが、アクセス修飾子の付け忘れや、enum で表せる状態を Bool の組み合わせで持つ箇所が1〜2か所ある |
| 2 | 強制アンラップや `try!` が実行時に失敗しうる場所にある。または並行性の警告が残っている |
| 1 | Swift の型や Optional の仕組みを使わず、他言語の書き方をそのまま持ち込んでいる（文字列で状態を管理する等） |

## UIKit 特有の確認手順（採点時に行う）
| 確認項目 | 方法 | 関係する観点 |
|---|---|---|
| ViewController の肥大化 | VC ごとの行数と、検証・保存・通信・整形の処理の有無を数える | 設計 |
| Auto Layout の制約衝突 | 縦向き・横向き・文字サイズ最大で起動し、コンソールの「Unable to simultaneously satisfy constraints」を数える | 動作 |
| 循環参照 | 画面を開いて閉じる操作を3回行い、`deinit` のログまたは Memory Graph Debugger で VC と ViewModel が解放されるか確かめる | 設計 |
| RxSwift・Combine の購読 | `DisposeBag`／`AnyCancellable` の保持場所と、クロージャ内の `self` の参照を確かめる | 設計 |

```
| 観点 | レベル | 点数 | 根拠 |

| 設計 | 3 | 15 | ListViewController.swift:120 で日付の整形を直接行っている |
| 可読性 | 4 | 20 | |
| テスト | 3 | 15 | 境界値（99・100）のテストがない |
| Swiftらしさ | 3 | 15 | Store.swift:30 に private の付け忘れ |
未確認：実機での確認（シミュレータのみ）
次に直すこと：設計（日付の整形を ViewModel へ移す）
```
